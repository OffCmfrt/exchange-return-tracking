00Read this first

This document assumes you know how to build a backend. It contains no advice about queues, migrations, caching or deployment. What it contains is the part you cannot infer: what an Offcomfrt athlete is, what happens to them, and the handful of rules that look arbitrary but are not.

Three things are worth knowing before you read the object model.

  • The programme is still being designed. Every threshold, rate and reward in §07 will change, probably more than once. They belong in configuration from the first commit. The shape below will not change.
  • The ladder counts down. Athletes go from Comfort Level - 5 to Zero Comfort. Seniority ascends as the displayed number descends. See §02 and rule 2 in §06.
  • Two things are harder than they look — the ledger and the level engine. Everything else is CRUD over the model below. Build those two first and prove them before anything depends on them.

The mistake this table exists to prevent

display_number runs 5→1 and then goes NULL. ordinal runs 1→6. A senior athlete has a higher ordinal and a lower display number. Any expression comparing display numbers to establish seniority is inverted and will promote and demote the wrong people silently. Put that sentence in the column comment.

// zero activity    -> decay 5 per 30 days, floor 0

The only two places XP moves

→ APPROVED creates it; → CLAWED_BACK reverses it. No other transition in this machine touches a balance. The same is true of the order flow: a paid attributed order creates, a refund or cancellation reverses.

Shipment request

Linear with exceptions: REQUESTED → APPROVED → ADDRESS_CONFIRMED → PACKED → DISPATCHED → IN_TRANSIT → DELIVERED, with CANCELLED available before dispatch, and NDR → RTO | DELIVERED and LOST after it.

DELIVERED is load-bearing. It stamps shipment.delivered_at, which starts the trial clock and anchors every trial deadline. Approval date is not used for this anywhere — a slow courier must never shorten an athlete's window.

06Domain invariants

Eight rules. Each one is nearly free to honour now and expensive to retrofit later. They belong in the README and the review checklist.

  1. XP and coins change only by inserting a ledger row. Cached totals on influencer are written in the same transaction and are reconstructible by replay. Nothing increments them directly.
  2. Compare ordinal, never display_number. Seniority ascends while the label descends. This is the single most likely source of a silent, serious bug in this system.
  3. The ledger is append-only. Corrections are new rows carrying reverses_entry_id. Nothing is edited or deleted, including by an admin.
  4. Level is derived, never assigned. Only the level engine writes influencer.level_id, and every write pairs with a level_history row. Admin overrides use the same path with direction = OVERRIDE and a mandatory reason.
  5. Promote one level per evaluation, then re-enqueue. An athlete who crosses two thresholds at once earns two promotions, two history rows, two prizes and two messages. Jumping swallows one the athlete earned.
  6. Commission is frozen at order time. attributed_order.commission_rate is stored on the row. Recalculating historical commission after a promotion makes reconciliation impossible.
  7. Everything inbound is idempotent on the sender's event id — enforced by a unique constraint, not a lookup-then-insert. This applies to Shopify, the courier and the payment gateway alike.
  8. Athlete-facing routes serialise through a whitelist. A field added to a model later must not be able to appear on a public page by accident. See §09.

08Service boundaries worth drawing now

Not a prescription for how to structure the codebase — just the seams the domain actually has. Seven contracts; everything else can be organised however you prefer.

LedgerService
  award(influencerId, currency, amount, sourceType, sourceId, idempotencyKey) -> Entry | NoOp
  reverse(entryId, reasonCode, actorId) -> Entry
  balance(influencerId, currency) -> int
  replay(influencerId) -> int            // reconciliation + tests

LevelEngine
  evaluate(influencerId) -> Promoted | Candidate | Unchanged
  promote(influencerId, toLevelId, reasonCode, actorId?) -> void
  override(influencerId, toLevelId, reasonCode, actorId) -> void

TransitionService
  move(entityType, id, toState, actor, reasonCode?) -> void
  // validates against §05; illegal transition -> 422, never a silent write

TokenService
  issue(scope, influencerId, subjectId?, ttl?) -> rawToken   // stores hash only
  resolve(rawToken) -> {scope, influencerId, subjectId} | null
  rotate(influencerId, scope) -> rawToken
  revokeAll(influencerId) -> void         // called on discharge, same txn

StandingService
  recompute(influencerId) -> int

AttributionService
  ingestOrder(payload) -> AttributedOrder | null
  reverseOrder(shopifyOrderId, refundedAmount) -> void

PayoutService
  buildBatch(periodStart, periodEnd) -> Batch   // VERIFIED methods only
  send(batch) -> void                           // idempotent per (influencer, period)
Stub these behind interfaces

Four external dependencies that should not block domain work. Define the interface, return fixtures, implement when the accounts are live: WhatsApp sender (templates are pending Meta approval), Shopify client (codes, draft orders, fulfilment), platform metrics fetcher (Instagram and YouTube), VPA validator (gateway onboarding). The ledger, the level engine and every state machine can be built and fully tested without any of them.

09Exposure rules for athlete-facing routes

Athletes reach the system through unguessable links rather than accounts. Three constraints follow from that, and they are domain rules rather than infrastructure preferences.

ScopeLifetimeMay expose
PROGRESSPermanent, rotatable, revoked on dischargeComfort Level, XP, progress to next level, open task titles and deadlines, the ladder, leaderboard position. Never: address, phone, email, bank or UPI detail, KYC, order history, or any rupee amount.
SUBMISSIONUntil due_at + 14 days; reusable while the assignment is openOne assignment's brief, deadline and submission form. Nothing about any other assignment.
ADDRESSSingle use, 7 daysOne shipment request's address and size picker.
ONBOARDINGSingle use, 14 days, dies on completionProfile, socials, terms, KYC upload.

A token grants exactly its own scope. Possession of one must never reveal another athlete's data, another assignment, or a field outside the list above. Implement the PROGRESS payload as an explicit field whitelist so that adding a column to influencer later cannot leak it.

Anything financial requires a step-up — a one-time code to the registered phone, not a permanent link. That applies whenever earnings, payouts or payout methods become visible to athletes.

10Undecided — do not model around guesses

Four open questions. Each one has a shape in the model above that will hold either way, so none of them block you — but do not infer an answer and bake it in.

OpenWhat to do meanwhile
Do coins convert to cash, or only to product?Build the coin ledger either way. Leave redemption fulfilment as a shipment request; do not build cash-out until this is settled.
Commission as a percentage, or flat per order?commission_rate plus commission_amount on the order row supports both. Store the computed amount; do not derive it at read time.
Are trial tasks identical for everyone, or scaled by audience size?task_template.level_gate_id exists; an audience-band variant would be a second nullable gate column. Do not assume a single global trial set in your queries.
Who reviews, and what is the turnaround promise?Affects reviewer seats and routing, not the model. Build the review queue unassigned for now.
